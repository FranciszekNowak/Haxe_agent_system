# ADR-060: Per-execution cost in the managed comment footer (time-window image attribution)

Supersedes (in part): ADR-057's "Footer semantics" decision (managed footer = cumulative task `SUM`).
Depends on: ADR-057 (`Write Cost Field (v1)`, the cumulative cost field), ADR-055 (image generation via
the self-hosted MCP server), ADR-035 (per-run cost logging, `Log Model Run (v1)` as the sole FX/PLN owner),
ADR-053 (managed-agents lane).

## Context

Two user-facing surfaces expose run cost: the ClickUp **`[AI] Koszt akcji [PLN]`** field (the running
task total) and the **comment footer** each agent reply carries (`…(model: X, koszt: Y PLN)`).

ADR-057 unified the field write into `Write Cost Field (v1)` and, for the managed lane, **sourced the
footer from the same cumulative `SUM(agent_runs.cost_pln)` over the whole task**. ADR-057 noted this
deliberately ("the `SUM` is at least as accurate and reuses one query"). In practice it is wrong for a
*per-comment* footer: every managed reply showed the task's **running total**, not the cost of the
execution that produced that reply. On a task with several runs the footer climbed (e.g. 14 → 24 → 26
PLN across replies on one task) regardless of how cheap the individual reply was. Reported 2026-06-24.

Separately, the managed footer carried **no image cost at all** (`total_image_cost_pln` was hardcoded `0`),
even though image-generation is often the dominant cost of a managed run.

Two requirements followed: (1) the footer must show **this execution's** cost, and (2) that figure must
include the **images generated by this execution** — and managed image cost must also reach the cumulative
field `SUM`.

### What was already true (and corrected a stale assumption)

Investigation found managed image-gen cost rows **already carry the real `clickup_task_id`** (the agent
passes it as a `generate_image` MCP tool argument — ADR-057 Amendment) and `Write Cost Field`'s per-task
`SUM` has **no modality filter**, so **requirement (2)'s cumulative half was already satisfied**: image
cost is in the CU field. A node note claiming image rows "carry a null task id … not yet in this SUM" was
**stale** and was corrected. The remaining work was the footer.

### The constraint that shaped the design

Image generation runs through the **self-hosted MCP server** (ADR-055); the in-session image handler is
dormant. By ADR-055's deliberate design the MCP boundary exposes **no session/correlation context** to the
handler — only the tool arguments the model fills. So there is **no per-execution key** (no `session_id`,
no run id) on image cost rows, and adding one would require either a second agent-supplied argument
(more agent-dependence, plus editing the fragile `toolWorkflow.workflowInputs.schema[]` — the ADR-057
footgun) or threading a key through five workflows + a DB migration. The only signals reliably present on
an image cost row are `clickup_task_id`, `triggered_by='image_mcp'` (hardcoded, migration 036), and
`created_at`.

## Decision

The managed footer shows the **per-execution** cost = the session's own text cost **plus** this
execution's image cost, attributed by a **time window**, not by a correlation key.

1. **Session text cost** — `Execute Agent Session (v1)`'s `Final Return` surfaces `cost_pln` (the session's
   own PLN cost from `Log Session Cost` → `Log Model Run`'s `cost_pln_total`); the orchestrator's managed
   `Call Post Reply` uses it as the footer `cost_pln` (replacing ADR-057's cumulative `total`).

2. **Per-execution image cost (time-window)** — `Resolve Lane` captures `since_ts = now − 5s` **before** the
   session runs (the 5s buffer absorbs n8n↔DB clock skew). A new orchestrator Postgres node
   `Sum Execution Image Cost` computes
   `SUM(cost_pln) WHERE clickup_task_id = T AND triggered_by = 'image_mcp' AND created_at >= since_ts`,
   i.e. only **this run's** image rows (prior runs' image rows are minutes+ older, so the window excludes
   them). It is passed to Post Reply as `total_image_cost_pln`, which Post Reply already adds to `cost_pln`.
   Net footer = session text cost + this run's images.

3. **Cumulative CU field unchanged** — `Write Cost Field (v1)` still writes
   `[AI] Koszt akcji [PLN] = SUM(agent_runs.cost_pln)` over the whole task (all-time, all modalities). Image
   rows are already in it (see above).

4. **Reliability guard** — `Img Cost Missing?` fires an `agent-orchestrator/image-cost` WARN (ADR-025 seam)
   when images **were** delivered (render `image_manifest` non-empty) but the windowed image cost summed to
   `0` — catching the window/skew/filter failure modes. The agent-omits-the-task-id mode is already caught
   at generation time by the `image-mcp/missing-task-id` WARN. The image-sum node is fail-soft
   (`onError: continueRegularOutput` + `alwaysOutputData`): a transient DB miss falls back to `0` and the
   reply still posts.

### Why time-window, not an explicit correlation key

A correlation id (e.g. the triggering comment id on each image row) would be precise and would not degrade
under same-task concurrency. It was **rejected as the default** because it requires editing the fragile MCP
`toolWorkflow.schema[]` (the documented drift footgun, ADR-057 Amendment), adds a **second** agent-supplied
argument the model can forget (compounding agent-dependence), is not universal (scheduled/form runs have no
triggering comment), and would need a migration or column reuse — disproportionate for a footer figure when
the cumulative field and the generation-time WARN already exist. The time-window reuses columns that are
already populated and touches no agent-facing or MCP surface.

## Consequences

- The managed footer now reflects the cost of the reply it sits under, image cost included. Verified live
  2026-06-24 on the moodboard test task `869dux9ne`: a single-image managed run rendered
  `koszt: 3.2939 PLN` = `2.789038` (Opus session text) + `0.5049` (one Gemini image, `image_count=1` from
  the window), the `Img Cost Missing?` guard correctly did **not** fire, zero CRITICAL alerts (one unrelated
  transient `files-api/fetch-failed: 504` WARN), and the cumulative CU field was left consistent with the
  data. Test `agent_runs` rows deleted afterward.
- **Known limitation (explicitly accepted):** two runs on the **same task** whose windows overlap (both
  generating images within the same interval) will cross-count each other's image cost in the footer. For a
  5-person team running the managed lane this is rare. It is **not** covered by a guard (counts can't cleanly
  distinguish it from generated-but-not-delivered images); the bulletproof fix is the rejected correlation-id
  key, available later if concurrency rises.
- The session text-cost surfacing (item 1) means `Execute Agent Session`'s contract now includes `cost_pln`;
  the cumulative `total` from `Write Cost Field` is no longer read by the footer (still written to the field).
